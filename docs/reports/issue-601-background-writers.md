# Background writer contention investigation

## Investigation before changes

The host must refuse a busy turn when it cannot replay a previously reduced request, rather than sending unreduced history. The reporter's supplied stack does not identify whether this was a first turn: there is no session ID, replay diagnostic, or saved-request state in the supplied stack. `completeness=partial` describes missing token accounting, not absence of an LKG slot. Pi attempts to replay the last-known-good (LKG) reduced request if snapshot preparation succeeded, compaction is enabled, and emergency recovery is not armed. Replay can also decline for missing anchors or tail identity. A first turn without a saved request is one possible explanation, not an established fact.

There is no `pi-write-transaction.ts` at this revision. Pi registers its handler via `pi-context-refusal.ts`. At the original base, Pi did not establish `withSqliteTransformPass`. The first fix added that scope, but the review correctly found that it bounded only explicit BEGIN, not implicit writes: both Pi and OpenCode autocommit writes could still block on their connection timeout (Pi boots with 5000 ms). The revision now bounds both shared paths, with one aggregate 250 ms synchronous admission allowance per awaited transform. Neither host reruns partially executed callbacks. OpenCode's separate async privileged preflight can retry acquisition alone for 16.5 seconds, yielding between short 25 ms native waits. A 3.2 second hold exceeds the latter. Pi's catch attempts LKG and then a size-checked raw fallback; that raw fallback on *storage busy* conflicts with the project's stricter replay-or-refuse policy and will be removed for busy errors (ordinary non-storage errors are separate).

`session_project_backfill` logs lease acquisition, reading or updating the one lease-state row for the harness, **not** a transaction covering discovery or the whole backfill. Its timer starts before BEGIN, so reported `held=3208.9ms` can include waiting for somebody else's lock. Discovery, filesystem identity resolution, and pagination are already outside transactions. Each session binding/repair commits separately (100 repaired chunks maximum), with yields during discovery. The attribution needs to time from successful BEGIN.

Embedding registration performs DISTINCT legacy-model discovery and an unbounded mis-scoped chunk update while holding the writer. GC limits deleted vectors to 250 but has no limit on empty identities and does legacy-model/existence discovery under the writer. A row limit alone is not a time bound for expensive scans or large vectors.

## Initial implementation measurements (superseded where noted)

Registration now discovers historical model IDs and incorrect project assignments **before** taking the writer. It inserts at most 25 missing model markers per scope and repairs at most 25 chunk assignments per registration. Further registrations resume from the remaining database rows. Discovery-complete state is remembered per connection/project/scope/model; once the slice is exhausted, steady-state registrations do keyed marker checks and bounded repair checks, not repeated DISTINCT vector scans. Repair rechecks session ownership under the write lock. Each GC transaction commits at most 25 vectors and examines at most 25 expired identities, including empty identities; it rechecks a marker's activity after acquisition. Memory/commit selection uses the existing embedding primary-key index through parent IDs rather than reading vector-bearing rows to filter by project. The timer drains these short committed slices with an event-loop yield between them and a 2 s budget per maintenance job per tick. Pi's cached-config registration also drains pending discovery/repair instead of skipping it for the process lifetime.

The non-empty FTS-map batch measured 103.89 ms for the original 500-row default. It now caps even explicit oversized requests at 100, keeps the bounded FTS selection, mappings and cursor in one transaction. Reading FTS owners under the writer prevents rowid reuse between discovery and recording. Its existing asynchronous drain yields between commits.

For LKG, a simulated future retention cutoff on the *real* prefix backlog made 377 slots eligible. The old deletion statements took **6600.37 ms** before rollback (excluding rollback time). The new maintenance call removes at most one stale metadata row and 25 prefix slices, revalidating retention and absence of a live slot under the writer. Removing metadata first means no partial prefix is replayable; later yielded slices in the same job budget, or subsequent ticks after the budget expires, reclaim orphan slices. It is safe to capture a new slot while cleanup is in progress: cleanup never deletes chunks owned by a live slot. The seven-day retention policy is unchanged. The previously unlabelled writer now reports `lkg_stale_gc`.

Both orphan sweeping and pending cleanup now split work into **25 owned rows from one table per transaction**, plus small retry/slot metadata changes. FTS records and their rowid locators are paired in the same commit. The durable pending row is retained until no eligible data remains. Discovery is outside the writer; a `PRAGMA data_version` check under the writer defers a stale plan if another connection committed changes. Rust acknowledgements still gate host deletion, and the final project coordinates and retry marker retire together. Pending jobs rotate by last-attempt time, so a large session does not monopolize later sessions. An orphan is rechecked against its owning host before every resumed slice: unavailable authority defers it, a restored live session cancels the orphan marker without deleting live data, and the generic pending-cleanup timer cannot process orphan markers without that authority. ### Why production LKG replay was unreachable

`git log -S` identifies an unwired contract, not a later removal of production wiring. `af013e6fb13ee82a21ebc3ed09a0e6510468517c` (2026-09-12) added the handler's four-argument replay fit call. `f026f1fe64712aedb69393a4c55f5964bb040709` (2026-09-22) added the required complete system/tools observation to the guard but did not change that handler call. `076000f8a1199ffd53ab5686afd27d7060334841` (2026-09-22) supplied observations to the direct coordinator test only and changed installed-handler small-replay tests into refusals. No production handler commit supplied `toolDefinitionTokens`; the intended repair covered a different, proxy test call site. Thus a valid saved prefix could still reach `completeness=partial`. The supplied incident stack cannot distinguish that wiring defect from first-turn or metadata absence.

The installed handler now supplies a complete conservative envelope **only for validated LKG prefix-plus-tail replay**, never raw busy fallback. It reads `ctx.getSystemPrompt()` and every registered definition from `pi.getAllTools()`, including name, description and full JSON schema; counting inactive definitions and serialized wrappers is conservative. External schema objects are serialized once so token and byte guards price the same snapshot. Frozen session calibration is used only for the matching measured model; unmatched/unmeasured or family-only freezes use `max(2.0, largest measured ratio)` through the shared unknown-model fit rule. Both calibrated total mass and the four-serialized-bytes-per-token proxy must fit the existing model-keyed usable hard limit. The proxy includes the system/tools envelope, not just messages. Missing/throwing required APIs, malformed/cyclic/incomplete schemas, an unavailable exact tokenizer, an uncountable newly appended tail or an unavailable limit refuse. Previously accepted prefix images can be priced through correlated provider usage; without that basis, an uncountable prefix also refuses. These are host-metadata estimates under the existing static safety policy, not newly instrumented provider-wire measurements.

### Preferred provider-measured basis

A terminal `message_end` observation now binds provider-reported input usage to the in-memory capture plan only when its model/provider match, its timestamp is not older than the capture, and its real JSONL parent is the captured request's last input. Before Pi appends the reply, the current leaf supplies that parent; already-appended runtimes can supply the exact reply's explicit parent. On replay, the first appended assistant's complete usage signature and real parent must match, along with the slot's capture sequence, capture time, model/provider and exact prefix. A newer capture, a different model/provider, failed/aborted reply, unknown input ownership, missing cache counters or unavailable parent lookup cannot supply this basis. This association is deliberately in memory: a restarted process falls back rather than guessing that historical usage belongs to a stored slot. No schema changes are needed.

The input baseline includes `input + cacheRead + cacheWrite`; a larger complete `totalTokens - output` is retained conservatively. The preferred bound is **that measured input count plus max(frozen-ratio tail mass, serialized-tail bytes / 4)**. The accepted assistant's reply itself is part of the new tail, because it was not an input to its own request. The preferred basis also requires the same complete current host system/tools fingerprint and active-tool subset; changed or unobservable metadata falls back to the all-definitions host estimate. This prevents a changed tool registry or activation set from borrowing the old measured count.

Provider additions and hook mutations already present in the accepted captured request are therefore included in its reported input usage. The fallback does **not** count later provider transformations: installed pi-ai 0.87.1 Anthropic adds an OAuth identity block, strict-schema fields, cache/deferred-tool wrappers and a placeholder tool after host introspection; hidden server-side scaffolding is not client-observable. `before_provider_request` hooks can mutate the final payload afterward. Their mass is estimated by static policy on the fallback, not measured. Even the preferred baseline cannot predict changed future hook/scaffolding behavior; an under-estimate is left to provider rejection and the existing overflow detector, not fail-open raw delivery. A failed replay does not replace the cached prefix. A larger provider-wire instrumentation contract is out of scope.

The installed-handler test uses reported input 300000 against the current smaller usable limit to prove the measured count causes refusal even though the local prefix is tiny. The same usage tagged with another model is ignored and the complete host fallback replays successfully. Latest production-timeout trials: complete fallback **261.60 ms, 0/1 refused**; measured over-limit basis **253.97 ms, 1/1 refused**; other-model usage **262.33 ms, 0/1 refused**; missing tools API **264.81 ms, 1/1 refused**; throwing system API **259.47 ms, 1/1 refused**; oversized tools **275.66 ms, 1/1 refused**; first turn during a 3.2 s hold **253.49 ms, 1/1 refused**. The earlier 80 ms bounded-writer trials remain 0/3 refused. These are deterministic workload trials, not a production refusal-rate estimate.

The 250 ms claim is the aggregate configured **foreground SQLite write-admission** allowance for a transform, not a wall-clock turn deadline. Declared detached background jobs get independent 25 ms native attempts and their own yielded work budgets. OpenCode's async privileged preflight remains separate. File I/O, tokenizer work, metadata reads, COMMIT/checkpoint execution and unrelated host/plugin callbacks are not certified by that allowance. The adapter covers the actual production `exec` and prepared `run/get/all` mutation paths; no callback is rerun after partial execution.
