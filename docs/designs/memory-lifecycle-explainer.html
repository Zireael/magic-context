A current claim set, not another event log

Remember what matters.
Keep the evidence of what changed.

Today, project memory accumulates facts. The proposed lifecycle separates what happened from what is still useful, gives each claim an evidence trail, and spends prompt attention without disturbing a warm cache.

Proposed · not implemented Local, self-contained explainer

Source of truth: Project memory lifecycle. “Today” means the implementation described by that design, not a new audit of your live store. The trials used copied stores and did not change memories.

01 / The one-minute version

Less prompt baggage. More accountable knowledge.

  • Keep episodes in compartments; keep reusable claims in memory. A compartment is a saved, dated episode summary. Its fullest narrative is P1; P2–P4 are progressively shorter versions. It remains the source of evidence, not a second memory row.
  • Extract first, reconcile second. The historian reads the new transcript without a project-memory block, then compares candidate facts with relevant claims from the whole eligible owned project pool.
  • Separate importance from freshness. Importance is the consequence and breadth of not knowing a claim. Freshness measures reinforcement and age. Their product chooses attention; age alone never proves a claim false.
  • Revise without erasing. Keep previous prose, metadata and evidence in history. Superseded rows leave ordinary search, but deliberate history lookup and audited restore remain available.
  • Keep background work off the cache clock. Reweight only at a rebuild already needed for another reason. Bulk repair and its undo wait for that rebuild before entering the primary prompt.
  • Earn automation in stages. Start with shadow decisions—recorded but not applied—and operator-approved transitions. The trials support a better reconciliation prompt, not autonomous rewriting or retirement.

03 / The new model · proposed

A memory is a claim with a reason to remain useful.

Each live claim gains a decay class, distinct evidence records, a proof count, a last-reinforced time and append-only history. Citations identify the project, conversation and harness, compartment and message range. Evidence must still be resolvable; an import timestamp is not a proved occurrence date.

Constant freshness

Standing rule

An explicit user instruction or an explicitly saved operating rule, with the original instruction/save evidence.

Example: the user-stated process-termination prohibition in the rescore trial. Inferred imperative wording does not qualify.

Exit: an explicit, evidenced revocation or replacement. Silence or a code change cannot revoke it.

Slow decay · months

Structural fact

Architecture, configuration semantics, an external limit, a naming decision or a mechanism with continuing consequence.

Example: the shared Transcript abstraction described in the rescore trial—a mechanism reused across message representations.

Refresh: a new observation or genuine confirmation restores freshness.

Fast decay · days to weeks

Situational fact

Current, changeable state that matters for continuing work: a temporary environment constraint, open operational state or provisional configuration.

Example: the temporary fleet hold in the rescore trial. Preserve its uncertainty; a plan is not an accomplished result.

Exit: decay reduces attention; evidence, not age, decides a correction or retirement.

Episode is not a live memory

Episode

Something done, investigated, released or measured without an independently reusable claim.

Example: the codebase dead-code cleanup in the rescore trial, when it records only work completed rather than a lasting constraint.

Keep: the compartment narrative. Archive legacy episode-memories only after reviewed backfill.

Examples illustrate the proposed class definitions, not existing class labels on trial rows. Classes are separate from content categories and permanent status. Split mixed rule/state claims rather than averaging their decay. Design §3 · Rescore examples

Importance × freshness

Importance reflects consequence of not knowing and breadth of applicability, mapped by a reviewed rubric to the existing integer scale. It is stable between reviews; repetition does not increase it. Freshness handles elapsed time since accepted reinforcement.

weight = importance × freshness

Standing rules: freshness = 1. Other live classes: freshness = 2−age / class half-life. Capture one clock and policy at a natural rebuild. This is not a live decay timer and not the compartment algorithm, which uses distance from the newest compartment.

The horizontal axis is elapsed class half-lives, not days. The structural and situational curves have the same normalized shape; their calendar timescales would differ. All plotted weights are illustrative arithmetic from the design’s formula, not trial measurements or proposed tier cutoffs.

With selected reinforcementWithout reinforcement

Importance 50: without reinforcement, weight halves with each class half-life. Reinforcement resets freshness, not importance.

Reinforcement signals, strongest first

  1. “Covered by #N” in reconciliation. Real work re-observes a fact fully covered by that target. Attach the new compartment evidence, even if the target was not in the primary prompt.
  2. Verify confirms the current claim against code. Save backing files, checked commit and result on the row. Mapping a file, skipping a check or refusing a rewrite is not confirmation.
  3. Actual agent use. A scoped citation in the answer or explicit consumption/expansion of a search hit can refresh attention. Merely returning a search result cannot.

Distinct grounded observations count as proofs; usage alone does not prove truth. Retries, prompt copies, duplicate citations, classify and cue compression add no reinforcement. Old backfilled evidence keeps its old observation time; repair time is not new evidence. Search counts are telemetry, not permanent promotion. Design §3

Attention is tiered; knowledge is not discarded.

  • Prompt text: protected standing rules first, then highest-weight whole claims within the text budget.
  • Mural cue: remaining cue-worthy claims with current cues, within the image budget, on a vision-capable model.
  • Search-only: low weight, stale/missing cue, image overflow or unselected claims on a non-vision model. Full current text remains searchable.
  • Archived, via explicit history: reviewed episodes and superseded/retired claims. Not a decay tier, not an ordinary search hit—even by ID.

Tier floors and cue capacity are open. Keep the configured text budget in initial shadow replay; no trial establishes a new budget. If protected rules cannot fit, report a capacity problem rather than silently substituting vague cues. Design §3

04 / The new write path · proposed

Give extraction and reconciliation separate jobs.

What each reconciliation action means
ActionDurable effect
NewCreate an independently useful claim with origin, evidence, proposed class and provisional importance awaiting review.
Covered by #NThe target alone covers every claim. Keep prose and importance; attach distinct evidence and reinforce. Joint coverage needs explicit mapping or review.
MergeRefine a coherent facet, preserving all still-valid claims. Keep the survivor ID; archive other source rows with successor links and their histories.
UpdateRevise the same property on the same ID. Preserve unrelated claims and append state-update history.
ReplacesAn evidenced contradiction or revocation creates a successor revision/row and archives the predecessor. Revocation with no surviving claim is an audited archive, not an empty live row.

What the gate catches

Missing identifiers, paths, units, refusal codes and named keys; invented target clauses; non-verbatim evidence; missing inventories or unevidenced replacements. An actual wrong raw rewrite was rejected for fabricated ellipsis text.

What it cannot establish

Whether a real quotation contradicts a claim. Whether surviving tokens retain their operative meaning. Whether “new” is already covered. It missed a weakened detach guarantee and a workaround mistaken for removal of an API limitation.

Rejected rewrite → old row untouched, original fact pending. The proposed design does not repeat the trial’s automatic all-new fallback. Approval remains required until independent preservation/contradiction review passes held-out tests.

05 / Non-destructive changes · proposed

Current truth on the row. Previous truth in history.

Using the same source-backed transition, the row keeps its ID and gives actionable current limits. “Was X, now Y” belongs in current prose only when the transition itself helps future work.

Before · #23697

Attachment-cache limit: 256 MiB.

Attachment scope and eviction behavior are still valid and must survive the update.

After · same ID

Attachment-cache limit: 384 MiB total / 288 MiB per entry.

Retain the same scope and eviction behavior. The earlier bound is history, not a competing search result.

{
  previous_text: "prior complete prose, including the 256 MiB bound",
  changed_at: apply time,
  reason: state_update,
  evidence: source compartment and qualified message range,
  source_ids: [23697]
}

This illustrates the journal shape; source prose, evidence coordinates and dates are intentionally not fabricated. The full revision journal also records old class/category/importance/status, hashes, actor, rubric/model, observation key and successor relationships.

  • Update: the old revision leaves ordinary search; the current row remains. History preserves the full earlier prose and metadata.
  • Merge or replacement: archived source/predecessor rows leave semantic, full-text and explicit-ID memory search, and future cue selection. Successor links lead to current knowledge.
  • Restore: a deliberate, conflict-checked new revision. Undo restores metadata as well as prose, without deleting intervening history.

Already-served text and images remain frozen until an independently authorized correction/fold. Ordinary restore waits for a natural fold; bulk repair and its undo have the stronger barrier described below. Design §4

06 / Sweeps & the one-time fix-history backfill

Maintain the live set. Repair the past with consent.

Verify: finish the accounting

Write confirmation, complete file mappings, checked commit, evidence and reinforcement together on the correct revision. Audit legacy mismatches on a copied store; uncertain matches need a new check. Do not reset reinforcement to repair time.

Classify: break score anchoring

Hide the candidate’s current score. Use a versioned consequence/breadth rubric and fixed human-scored anchors. Review class eligibility against origin evidence, then rotate an overdue cohort—no forced histogram or every-run rescore.

Stale review: propose, do not presume

Low weight and long silence select a bounded backlog. Retrieve newer same-facet evidence and current code with caller context. Preserve uncertain or partly true entries; retire only with operator approval.

Events: repair optional provenance

Re-anchor useful causal/correction events and copy essential evidence into history. A trajectory change caused by a test or self-review is not a user instruction. Keep events initially; evaluate their additional value before retiring unused kinds.

One-time project repair, after the live path works

  1. Inventory and preview. Freeze eligible IDs, source revisions, registered histories and missing evidence. Show workload, calls/tokens/embeddings and a provider-based cost envelope; disclose unknown billing. Confirm project, budget and model profiles before paid work.
  2. Trace evidence. Match memory to compartments with compatible embeddings and lexical fallback. Check complete P1 and expand source when needed. Record first occurrence, distinct observations, latest reinforcement and cited transition proposals; similarity alone changes nothing.
  3. Classify. Blind-score with the new rubric and origin evidence. Flag episodes and possible rules lacking explicit origins.
  4. Resolve transitions. Order evidence by occurrence time, preserve valid claims and use the same approval-gated, revision-checked history applier. Newer does not automatically mean truer.
  5. Archive episodes. Only after evidence is recoverable and classification approved. Keep the compartment record and old memory audit.
  6. Rescore compartments. Prefer title + episode type + P1. Write score overlays, not base-row updates. Do not rewrite summaries, raw ranges or original messages; emit no new facts.
  7. Review and adopt. Show proposed, approved, applied, failed and stale items with before/after metadata. Search can reflect approved state now; primary prompts wait for each conversation’s next independently required baseline rebuild.

P1-only rescoring is the recommended arm, not an exact-score oracle: an unchanged rerun crossed bands for 10/60 compartments, with mean absolute change 4.33. Extra P2/recent titles showed no quality advantage. The wording trial’s intervention change 4.34 was below repeat noise 4.62. These compartment trials do not validate memory importance or half-lives. Pause/resume/cancel and audited undo belong to the same durable project job. Completion is per item; resume keeps the frozen input set. Reattach an admitted model run after disconnect rather than paying again while its outcome is unknown. Changed inputs become stale for a new preview.

07 / Cache safety · proposed contract

Background work changes knowledge, not the rebuild schedule.

m[0] is the frozen prompt baseline: memory text, compartment history and the paired mural image. m[1] is its saved additions/corrections. A HARD fold rebuilds that baseline. A SOFT refresh updates only the delta on a rendering opportunity already authorized for another reason. A defer replays both unchanged.

Which changes may appear when?
ChangeIndependent SOFTNatural HARD
Live new claim or textual correctionMay ride the already-authorized delta; never creates the opportunityFold into the new baseline
Age, proof, class or importanceNo reranking of existing attention or delta admissionsRecompute from the captured snapshot
Mural / compressed cuesNo image regeneration or swapUse current eligible cues with the same selected weights
Bulk repair, score overlays and undoWithhold bulk content, archives, additions and tier changesAdvance the conversation’s applied revision markers

The stronger backfill barrier needs a versioned prompt loader. Ordinary search sees approved canonical active claims. Rendering reconstructs the revision adopted by that conversation. Suppressing a mutation log is not enough: a later SOFT can reread changed rows and leak bulk repair through the delta.

Score repair needs render-only overlays. A bare compartment importance update can request an early HARD in Rust and invalidate full-row boundary identities. Leave base rows untouched; join effective scores only after a natural HARD is selected.

A marker-only Rust probe stays pinned. When checking whether a nominal fold would change bytes, use the last-applied scores, lifecycle revisions and clock—not pending repair. Otherwise repair itself could create the cache loss that appears to authorize it.

Privacy is not decay. Existing ownership, visibility and explicit privacy revocations keep their stronger invalidation paths. “Background work never busts the cache” must not suppress those safety actions.

This is a required implementation contract, not an invariant proved by the model trials. Shipping tests must compare actual served text/image/boundary bytes through defer, SOFT, HARD, restart and undo, with deliberate negative controls. Design §7 · Rescore cache contract

09 / Open questions & rollout

Recommendations, not hidden defaults.

Open decisions from the lifecycle design
QuestionRecommendation
Half-lives and tier floors?Open calibration
Replay fixed claims through folds and retrieval. Months versus days/weeks is direction, not fitted policy. Do not enable arbitrary numbers.
Can a token gate authorize rewrites?No. Keep approval; investigate independent claim-preservation/contradiction review. Preserve pending facts on abstention.
Hybrid context and lexical capacity?Reserve a distinct lexical candidate first. Ablate capacity with the long procedural rule; the top-eight experiment is not a production recommendation.
Which proofs count?Unique grounded observations, not attempts or prompt exposure. Separate correlated real work, code confirmation and use in diagnostics; use refreshes but does not prove.
Unknown-origin permanent rules?Review origins. Preserve instructions during shadow rollout; neither silently demote nor grant standing eligibility.
“Out of prompt” after archive?No future rendering of the retired row. Already-served bytes persist until independent correction/fold; show pending adoption. Privacy revocations remain stronger.
Is the versioned prompt loader worth it?Yes, if bulk repair must wait for HARD. Build it before backfill; otherwise explicitly renegotiate that promise.
Keep events?Repair optional grounded provenance first. Do not promote test/self-review pivots to standing rules; evaluate additional evidence value before removal.
Previous auto-promotion opt-outs?Require an explicit configuration choice before reconcile admissions. Preserve memory-off. Retire auto-promote and the unused retrieval promotion threshold only after the replacement path is available.
Can doctor run paid work?Read-only first. An authenticated project-bound broker is a separate executor decision; no ad hoc credentials or silent model choice.
Multiple registered histories?Preview all histories in the canonical project/scope and disclose missing/imported evidence. One long-lived conversation is an operating assumption, not a storage constraint.
Trials still open before activation
  • Fresh paired control: identical full-memory and stripped first-turn arms, judged durable-fact recall and omissions, actual cache/billing counters. Earlier historical-answer comparisons are not that control.
  • Next stale-reconcile trial: frozen true/stale/unsure labels, explicit preservation and caller evidence, false rule retirement, independent review and repeat variance. The completed curate result remains the failure baseline.
  • Other shipping evidence: lexical-slot/per-fact ablations, blinded memory class/importance calibration, copied-store verification/event audits, backfill evidence quality, job cost/retry behavior and runtime attention/cache replay.

Release order: earn each step

  1. Repair verification accounting first; no mass live repair.
  2. Shadow both-turn reconciliation and record what it would do.
  3. Enable operator-approved transitions with a durable pending queue.
  4. Blind classification and shadow attention tiers.
  5. Opt in to safe new admissions and reinforcements.
  6. Adopt cache-safe tiers after authority and runtime parity gates.
  7. Only then offer confirmed, reversible backfill. Autonomous transitions and retirement need a separate release decision.

Bounded implementation slices

All slices below come from the design’s rollout table. Expand a group for its deliverables. Feature activation stays off until cache and memory-owner parity pass across TypeScript OpenCode, Pi and Rust’s host/Broca completion paths.

Storage, correctness and admission contracts
  • Verification contract repair: row status, complete files, checked commit and reinforcement across writers.
  • Lifecycle schema and journal: evidence, pending facts, revisions, jobs, cleanup/export and writer/schema fingerprints.
  • Non-destructive applier: revision-checked, idempotent transitions/restore, metadata undo and archived-ID search exclusion.
  • Reconcile prompt and validator: anchored facts, readable inventory, reserved lexical slot and per-fact gates; shared TypeScript/Rust fixtures.
Conversation continuation, one runtime at a time
  • TypeScript OpenCode: same-child second turn, bounded retries, partial failures and memory-owner handoff.
  • Rust host: stage-aware claim/report protocol, retained child conversation and late-report defenses.
  • Rust Broca: distinct per-turn send identities, stage usage and unknown-outcome recovery.
  • Pi: same-conversation carrier, cancellation/context limits and routing; no fresh-session call advertised as cached continuation.
Attention and background review
  • Classification calibration: blind scoring, fixed anchors, origin/class output and repeat/privacy controls.
  • Memory attention projection: captured weight/time/revisions, shared text/mural selection and served-byte parity.
  • Bulk prompt adoption barrier: versioned loader, applied markers, pinned SOFT and marker-only probes; prerequisite to repair UI.
  • Stale/event sweeps: grounded proposals, event re-anchoring, preservation review and visible backlog; no automatic retirement.
Confirmed jobs, operator surfaces and configuration
  • Repair/score job engine: frozen inputs, overlays, costs, leases, source-revision checks and rollback.
  • Operator surfaces: slash preview/confirm/status/resume/undo; read-only doctor; later opt-in dreamer. Rehearse on a copied project first.
  • Configuration retirement: remove obsolete auto-promote and unused retrieval threshold across readers and interfaces, with explicit prior-opt-out handling.

Migration recommendation: land and rehearse the unreleased v95 performance/Pi marker batch first; the lifecycle migration is v96 at the earliest, with the actual version confirmed at merge. One context-database migration, no paid backfill inside it, and no weakening of old-writer authority guards.
